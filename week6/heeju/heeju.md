## 스케줄링, 선점(Preemption), 축출(Eviction)

**스케줄링**  
: 새로 생성된 파드를 클러스터 안의 **어떤 노드에 배치할지 결정**하는 과정

파드를 만들면 바로 실행되는 게 아니라, 먼저 API 서버에 저장되고 아직 어느 노드에도 속하지 않은 상태로 존재한다. 이때 kube-scheduler가 이 파드를 감시하다가 이 파드를 어디에 놓는 게 가장 적절한지를 판단한다.

여기서!! 스케줄러는 배치 결정만 하고, 실제로 컨테이너를 띄우고 관리하는 건 해당 노드의 kublet임

**kublet**  
: 노드 안에서 파드 실행 담당하는 에이전트

**Affinity vs Anti-Affinity**  
: 특정 조건을 만족하는 곳에 배치하거나 피하는 규칙

ex) Node Affinity: 노드 레이블 기준으로 파드가 배치될 수 있는 노드를 제한하거나 선호하는 규칙

**파드 오버헤드(Pod Overhead)**  
: 파드 실행에는 컨테이너가 쓰는 자원 말고도 추가 자원이 드는 것

ex) 네트워크 네임스페이스, cgroup 관리 등

<pre>
Pod 생성 요청
→ RuntimeClass 확인
→ overhead 자동 추가 (파드 생성 시 Admission Controller가 자동으로 넣음)
→ 스케줄링
</pre>

- 스케줄러는 컨테이너 요청량 + overhead 합쳐서 노드 자원 체크
- => 만약 자원 부족하면 스케줄 실패

**Pending**  
: 파드가 아직 실행되지 않고 대기 중인 상태  
보통 어느 노드에 올라갈지 아직 안 정해졌거나, 이미지 pull 중일 때도 포함됨

**다운스트림 통합자(Downstream Integrator)**  
: 스케줄러 결과를 받아서 같이 움직이는 다른 시스템들
ex) 클러스터 오토스케일러

**Cluster Autoscaler**.
: 노드 개수를 자동으로 늘리거나 줄이는 컴포넌트

- 파드 못 올라감 → 노드 추가
- 노드 놀고 있음 → 노드 제거

**스케줄링게이트(schedulingGates)**  
: 실행할 준비가 안 된 파드를 스케줄링 큐에 올리지 않기 위한 지연 장치

Pod 생성 후 바로 스케줄링하는 것이 아니라 기다리게 함. 아직 실행 조건이 안 갖춰진 파드를 스케줄러가 괜히 계속 보지 않게 함.

<pre>
Pod 생성 → 대기 → Gate 제거 → 스케줄링
</pre>

**파드 토폴로지 분배 제약 조건**  
: Pod를 특정 기준(zone/node)에 균등하게 퍼뜨리는 규칙  
-> 장애 발생 시 전체 서비스 영향도를 줄이고 가용성을 높이기 위함

**Taint**  
: 노드에 붙는 파드 거부 조건

**Toleration**  
: 파드에 붙는 거부 무시 권한 (노드에 들어갈 자격)

=> 노드에 어떤 테인트가 붙어 있어도, 파드가 toleration으로 그 조건이 적혀 있으면 그 노드에 들어갈 수 있음

**percentageOfNodesToScore**  
: 스케줄러가 전체 노드를 다 검사할지, 아니면 일부만 보고 결정할지 정하는 옵션

- 100% → 모든 노드 검사 (정확도 높음, 느림)
- 50% → 절반만 보고 결정 (빠름, 정확도 조금 손해 가능)
- 10% → 더 빠름, 대신 최적 노드를 놓칠 수 있음

높게 설정하면 더 좋은 배치가 가능하고, 낮게 설정하면 더 빠른 스케줄링이 가능함

**빈 패킹(Bin Packing)**  
: 파드를 빈 공간 많은 노드에 퍼뜨리지 말고, 이미 좀 차 있는 노드에 몰아서 넣자는 전략  
-> 리소스를 최대한 꽉 채워서 노드 낭비를 줄이는 스케줄링 방식

<전략>

- **MostAllocated**
  - 그냥 현재 많이 쓰고 있는 노드 우선
- **RequestedToCapacityRatio**
  - 사용률 비율 기반으로 더 세밀하게 점수 계산 가능 (가중치/커브 조정 가능)

**노드-압박 축출(Node-pressure eviction)**  
: 노드가 죽기 직전 kubelet이 자원을 확보하려고 파드를 강제로 정리하는 과정

kubelet이 계속 자원 상태를 감시하다가 자원이 부족해지면 먼저 노드 수준에서 정리 가능한 걸 치운다. (가비지 컬렉터, 안 쓰는 이미지 삭제 등) 그래도 부족하면 파드 축출 시작!

<축출 기준>

- 요청(request)보다 더 많이 쓰는 파드
- Priority 낮은 파드
- 얼마나 많이 초과했는지

‼️ **선점(Preemption)**은 scheduler가 높은 우선순위 파드 넣으려고 낮은 파드 밀어내는 것이고, **노드-압박 추출(Node-pressure eviction)**은 kubelet이 노드 자체를 살리려고 파드 밀어내는 것임

Preemption: 새 파드를 위한 자리 확보, Eviction: 노드 생존 확보

**API를 이용한 축출(API-initiated Eviction)**  
: 사람이 의도적으로 파드를 내리는 방식(안전한 종료 방식)  
-> 축출 API를 사용하여 생성된 Eviction 오브젝트로 파드를 정상 종료

**노드 선언형 기능(Node Declared Features)**  
: 노드가 지원 기능을 스스로 신고하고, 스케줄러는 그걸 보고 맞는 Pod만 올리는 기능

만약 없다면 스케줄러가 리소스만 보고 충분하다 생각해서 넣을 수 있는데, 실제로 기능이 부족하다면 스케줄은 성공해도 실행이 실패할 수 있음!! 그렇기 때문에 사용을 한다~
